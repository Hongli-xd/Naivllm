## 第零章 为什么做这个项目（开场必问）

**Q1 为什么做这个项目？**

简要：三个递进动机——①想真正吃透 vLLM 这类引擎的原理，读十遍
源码不如自己写一遍；②判断"再造一个通用引擎"没有意义，但
"垂直场景特化"有真实空隙；③RAG 知识库问答是需求最大众、负载
特征最清晰的垂直场景，值得用一个完整引擎来验证这个判断。

详细：先看清市场格局：vLLM 占"吞吐极致"、SGLang 占"前端表达力
（结构化输出/FSM）"、Ollama 占"易用性"，各守一个生态位——新人
做通用引擎等于重复劳动且永远追不上。但存在一个空隙：**单卡、
小 batch、按需启停的知识库问答**——这个切片上，通用引擎的很多
成本（启动税、通用调度、大而全的抽象）是纯开销，却没有任何一个
竞品专门照顾它。要验证这个判断，需要一个能自由改动的完整引擎
（在 vLLM 的 20 万行上做这些实验，每个想法都要穿过通用抽象和
社区评审），于是从零写了 3.5k 行。所以这个项目有双重身份：
**学习载体**（把论文级机制落到可运行的代码）+ **垂直假设的实验
平台**（最终的三方基准数字验证了假设成立）。这样回答同时展示了
技术判断力和产品思维，比"为了学习"高一档。

**Q2 为什么选 RAG 场景？别的场景不行吗？**

简要：三条标准筛出来的——需求最大众（生产 LLM 应用里 RAG 占比
最高）；负载特征与可做的特化精确匹配（长共享前缀→pin、抽取式
回答→n-gram 投机、小批延迟敏感→全图化）；不是玩具（企业知识库/
客服/文档助手是真实部署形态）。

详细：选场景的方法论是先列负载特征（前缀多长、输出多长、并发
多大、延迟多敏感），再找"通用引擎照顾不好、但现有技术能特化"
的组合。RAG 的三个特征恰好各接我们一项能力：文档前缀又长又共享
→钉驻缓存让热文档永不重算；答案就是抄文档 → n-gram 草稿命中率
天然高（实测 63–90%）；用户一问一等着 → 单请求延迟是硬指标、
冷启动决定"能不能缩容到零"。也评估过 alternatives 并说得出为什么
不选：代码补全与 RAG 同构但部署形态偏 IDE 插件、天花板一样；
Agent 多轮思考流输出几乎不复述上下文，投机收益低——说明这是
"筛出来的"而不是"随手挑的"。

## 第一章 投机解码（简历第 1 条）

**Q3 什么是投机解码？为什么能快？**

简要：让便宜的方式先猜 K 个 token，大模型一次前向同时验证 K 个，
按概率规则决定收多少——接受就白赚，拒绝也无损。快的原因：验证
K 个 token 和生成 1 个的成本几乎一样（GPU 一次算一批很划算），
平均每轮能收 2~6 个。

详细：先建立一个直觉——GPU 算力极快，但"每生成一个 token 都要
把整个模型跑一遍"。投机解码像**考试时先打草稿再对答案**：草稿
（n-gram 或小模型）几乎不要钱，对答案（大模型一次前向）可以把
草稿的 K 个位置**一起**判完，因为 Transformer 一次前向本来就能
并行算一排 token 的输出（prefill 就是这么干的）。成本对比：
K 次完整前向（逐 token）→ 1 次前向（K+1 个位置一起）。只要草稿
猜得准（我们场景 63–90%），吞吐就上去了；猜不准也不会"错"——
被拒的位置由大模型自己的输出顶替，数学上保证最终结果分布与大
模型单独生成完全相同（见 Q7）。

**Q4 你的 n-gram Prompt-Lookup 具体怎么工作？**

简要：取已生成内容的末尾 n 个 token（n 从 8 试到 2），在整个
"prompt+已输出"历史里找最近一次一模一样的出现，把它后面跟着的
token 抄下来当草稿。实现用字节串 + `bytes.rfind`（C 实现），
单次查找微秒级。

详细：类比**输入法联想**：你打出"北京首都国"，输入法从你以前
打过的话里找到"国际机场"补全。RAG 里模型回答就是抄文档——
文档里写着"塔高 312 米"，答案也会写"塔高 312 米"，那么当输出
出现"塔高"时，拿这两个 token 去历史里一找，后面跟的
"312 米"就是高置信草稿。三个工程点：①**长 n 优先**（8 个
token 的重复比 2 个的更说明"在抄同一段"）；②**找最近一次**
（文风随上下文漂移，旧的重复不如新的可靠）；③**查找必须快**：
投机解码每一轮都要查一次，1200 token 的历史用 Python 循环切片
比较要几毫秒——比省下的时间还贵；把 token 编码成 4 字节定长的
字节串后调 `bytes.rfind`，这个函数在 C 层用硬件级内存扫描，
微秒级完成。"为什么不需要 draft 模型"：草稿来源是文本统计
规律，不是另一个神经网络，所以零额外显存、零额外前向。

**Q5 小模型 drafter 怎么实现？为什么强调"独立"KV Cache？**

简要：draft 是第二个 ModelRunner 实例——自己的分页 KV 池（记账
在 `seq.draft_block_table`）、自己的 decode CUDA Graph、自己的块
管理器；prefill 时与目标模型镜像各写一份 KV，草稿阶段跑 K 次图
回放。独立的原因：两个模型的 KV 形状、内容、确认进度完全不同，
混在一个池里既会写穿也没法各自图化。

详细：类比**主笔和实习生的两套笔记**：实习生（0.6B draft）先写
草稿，主笔（大模型）批改——两人笔记的页数格式（层数×头数）不同、
翻到的进度也不同（draft 永远比主笔多写 K 个草稿 token），硬共用
一个本子必然互相覆盖。工程上，ModelRunner 用 `table_attr` 参数化
成两份实例复用同一套代码；draft 的图里额外捕获了采样前的 logits
（随机拒绝采样需要草稿分布 p_d，见下一题）。什么时候不值得用：
draft 与目标同量级时（比如 0.6B 给 0.6B 打草稿）草稿成本≈验证
成本，必亏——我们用它验证了框架的正确性（100% 无损同样成立），
主打仍是 n-gram；真实收益组合是"0.6B 草稿 + 1.7B/4B 目标"。

**Q6 为什么要自己写"多查询 verify kernel"？**

简要：验证一次要同时算 K+1 个查询位置的注意力，而原 decode
kernel 一次只算 1 个查询。新 kernel 让这 K+1 个查询**共享同一份
KV 读取**（一次内存搬运服务多个查询），并用矩阵乘（tensor core、
fp32 累加）一次算出整列分数。

详细：decode 阶段的注意力是"1 个新 token 去看它全部历史"——
瓶颈在读历史 KV（内存带宽）。验证时是"K+1 个新 token 同时各自
看历史"：如果复用单查询 kernel 跑 K+1 次，同一份历史 KV 要从
显存搬 K+1 遍——纯浪费。多查询 kernel 把 K+1 个查询摞成一个
(BLOCK_M, head_dim) 的矩阵 Q，和同一块历史 K 做一次矩阵乘
`Q·Kᵀ`，**KV 只搬一遍**，分数一次全出。这就是"batch 维度上的
算术强度提升"：搬运的字节数不变，可计算的 FLOPs 翻了 K 倍，
GPU 从带宽受限往算力受限挪——同样的电费干更多的活。

**Q7 验证为什么要捕获成 CUDA Graph？**

简要：eager 模式下一次 28 层前向，GPU 实算只 ~5ms，但 Python
组 kernel、发 launch 的开销 ~26ms——CPU 成了瓶颈。把整轮验证
（含 kernel 序列和采样）录成图，每轮只做"拷数据 + 一次回放"，
省掉全部重复派工。

详细：类比**快递分拣**：GPU 是分拣机器人（极快），Python 是逐件
填单的实习生。eager 模式每件包裹（每个 kernel）都要实习生填一张
单（launch ~几微秒 + Python 开销），28 层 × 几十 kernel = 上千张
单，实习生累死机器人闲死。CUDA Graph = 把整条流水线**录像**：
第一次照常跑一遍录下"第几张单、什么参数"；以后每轮把新数据贴
到固定的单据模板上（静态张量原地更新），一按播放键（replay）
整条流水线一口气执行。约束是"流程必须完全固定"——所以块表、
序列长度都做成静态张量，采样也要用纯张量运算（Q17），任何
Python if 分支都不能出现在被录的代码里。我们按 batch 桶
{1,2,4,8} 各录一张，桶间 padding 行用 -1 哨兵置为"空操作"。

**Q8 拒绝采样为什么能"无损"？三种模式分别怎么工作？**

简要：贪心（T=0）——草稿等于大模型 argmax 才收，否则用大模型的
argmax，输出=大模型贪心解码；随机+草稿分布——按
min(1, p_t(d)/p_d(d)) 的概率收，被拒处从"残差分布"重采；随机无
分布（n-gram）——先从大模型分布抽一个样本，恰好等于草稿就收。
三者都保证最终输出分布严格等于大模型自己的分布。

详细：把大模型在每个位置的概率分布想成**一台老虎机的中奖率表**
p_t。目标是：不管中间怎么折腾，最终吐出的 token 服从 p_t。
有草稿分布 p_d 时（小模型 drafter）：对草稿 token d，以
min(1, p_t(d)/p_d(d)) 的概率保留。为什么对？分两种情况：草稿
的 token 在大模型眼里"更常见"（p_t≥p_d）→ 概率封顶为 1，全收；
"更少见" → 按比值打折，没收回来的概率质量恰好是 p_t(d)−p_d(d)
>0，把这部分**残差** relu(p_t−p_d) 归一化后抽一个补上——代数
上可展开验证：任何 token i 最终概率 = p_d(i)·min(1,p_t/p_d) +
残差项 = p_t(i)（Leviathan et al. 2023 的核心结论）。n-gram 没有
p_d 怎么办？换个等价玩法：先从 p_t 抽样本 x，若 x 恰好等于草稿
d 就"白赚"这个位置，否则直接用 x——输出永远是 p_t 的样本，
无损自动成立。贪心则退化为精确比对，我们用它做了最强验证：
**投机输出与不开投机的输出逐 token 一致**（`check_hf_alignment`
PASS 的依据）。

**Q9 "逐行因果掩码"是什么意思？**

简要：K+1 个验证查询里，第 i 行代表"生成到第 i 个位置"的时刻，
它只能看见自己之前的 token——每行的可见范围不同，掩码要按各行
的绝对位置逐行计算，而不是传统 prefill 的"一个三角形单"。

详细：Transformer 的铁律是**因果性**：第 n 个 token 的注意力只能
覆盖位置 0..n（不许偷看未来）。普通 prefill 的三角掩码里每行
范围不同但都从同一批行号推出来；验证场景更拧：K+1 行查询各自
站在不同的时间点（n−1, n, n+1…），第 3 行能看的比第 1 行多两个
token。kernel 里我们给每行存一个绝对位置 q_pos，掩码写成
`q_pos ≥ kv位置` 的一行一比——一行一个时间戳，"谁也骗不了谁"。
顺带一提 padding 行的 q_pos 设成 −1，掩码恒假 → 整行输出无效
但不影响别人，slot 也设 −1 不写缓存，这就是 Q4 桶式 padding
能安全复用一张图的原因。

**Q10 [vLLM 高频] vLLM 的投机解码是怎么组织的？和你的差异？**

简要：vLLM 是组件化路线——可插拔 proposer（ngram / draft model /
EAGLE）+ 统一验证前向 + GPU 批量拒绝采样器；V1 里投机批与普通批
统一调度。差异：它的 ngram proposer 做 top-k 多候选匹配，我们是
单候选右到左首个命中；它的验证走通用路径（attention 图外），我们
为验证专门图化。

详细：vLLM 把投机解码抽象成"提案-验证-采样"三段流水，任何提
案器只要给出 (token, 各自分布) 就能接——这是平台思维：不知道
用户跑什么负载，就把接口做宽。我们的取舍相反：知道负载是
RAG 抽取式，单链草稿的接受率已 63–90%，多候选树带来的"更高
期望接受数"要先付"验证变宽、kernel 更复杂"的成本，不划算；
而验证整轮图化（vLLM 的 piecewise 方案做不干净的一段）是我们
在单请求延迟上能追平它的关键之一。答这题的姿态：先讲清它的
组件化（体现你懂 vLLM），再说差异是**负载信息量**不同导致的
设计取舍，而不是谁对谁错。

**Q11 [vLLM 高频] n-gram / draft 模型 / Medusa / EAGLE / MTP 怎么选？**

简要：按"草稿质量 vs 草稿成本"排序：n-gram 零成本但上限受
"输出复述上下文的比例"钳制（RAG 恰好这个比例极高）；draft 模型
通用但要 K 次串行前向 + 双模型显存；Medusa 在目标模型上加多头
一次出树；EAGLE/MTP 在特征层自回归，接受率最高但要训练。RAG 类
负载 n-gram 性价比无敌，通用 chat 才值得上 EAGLE/MTP。

详细：把四代技术放在同一个坐标系里看——**草稿从哪来**：
统计复述（n-gram，我们的选择）→ 小网络猜（draft 模型，我们也实
现了，验证了框架通用性）→ 目标模型自己长出额外的头（Medusa：加
几个解耦的 LM head，训练目标是"下一 token"）→ 干脆在**特征层**
猜（EAGLE：猜 hidden state 而不是 token，因为 hidden 是连续的、
更好猜；DeepSeek-V3 的 MTP 是它的训练-推理一体化工程版）。越往
右接受率越高、工程与训练成本越高。一个关键技术分叉：链 vs 树
——树投机一轮验证多个分支（期望接受更多），要求验证 kernel 支
持树形因果掩码；我们的多查询 kernel 的"逐行位置"设计正是树形
掩码的退化直线形态，向树扩展只需把每行的 q_pos 换成树节点定义
的祖先集合——这是面试里能加分的"我留了扩展位"。

## 第二章 Prefix Caching 与工程化（简历第 2 条）

**Q12 KV Cache 是什么？为什么它是显存大头？**

简要：自回归生成时，每生成一个 token 都要重算所有历史 token 的
Key/Value 投影——把它们缓存下来就是 KV Cache。显存 ∝ 2 × 层数 ×
KV头数 × 头维 × 序列长 × 字节数，随上下文线性增长，长上下文下
远超模型权重本身。

详细：类比**复读机的笔记**：注意力机制里，新 token 要"回头看"
所有历史 token 的两种向量（K 和 V）。不缓存的话生成第 1000 个
token 时要把前 999 个全部重算——O(n²) 的浪费；缓存后每步只算
新 token 自己的 K/V，追加进笔记。代价是笔记要一直放在显存里：
以 Qwen3-8B 为例，每 token 的 KV = 2(K和V) × 36 层 × 8 KV头 ×
128 维 × 2 字节 ≈ 147 KB——8k 上下文就是 ~1.2 GB，而这类优化
的全部意义就是围绕"这份笔记怎么存、怎么复用、怎么搬运"展开
（分页 Q10、前缀复用 Q11、钉驻 Q12、跨机传输见速查版 J3）。

**Q13 Paged KV Cache（PagedAttention）解决什么？**

简要：把连续的 KV 显存切成固定大小的小块（block），序列用块表
记录"我的第 i 段在哪个物理块"——像操作系统虚拟内存的分页。
消除外部碎片、内部碎片 ≤1 块、相同前缀天然可以共享物理块。

详细：不分的坏处：每个序列预分配"最大长度的连续大条"，问 10
个 token 也占 4k 的位置（内部碎片），请求来了走了留下大大小小
的洞塞不下新请求（外部碎片）——vLLM 论文里利用率只有 20% 多。
分页后：笔记写满一页再领一页，页可以来自显存里任何位置；序
列真正持有的只是一个"页码表"。三个直接收益：①利用率冲到
90%+；②序列"长大"只是往表里追加页码；③**两个请求的前半段
相同 → 共享同一批物理页**（读同一份文档的 RAG 请求），这就是
前缀缓存的物理基础（Q11）。与 OS 分页的对应：块表=页表，
BlockManager=分配器，抢占=swap out，前缀共享=共享内存。

**Q14 前缀缓存怎么判断"可复用"？为什么哈希是链式的？**

简要：每个**写满**的块对内容做哈希，且子块哈希混入父块哈希
（h_i = hash(h_{i-1} ‖ tokens_i)）——指纹携带整条前缀的因果。
查表命中后还要逐 token 比对防碰撞。半满块和被回滚的块哈希必须
清空（未定稿的内容不能进索引）。

详细：类比 **git 的 commit 链**：每个 commit 的哈希包含父 commit
的哈希，所以"同样的改动"接在不同的历史上会得到不同的指纹——
这恰好是我们想要的：句子"塔高 312 米"出现在文档 A 和文档 B 里，
但它们的**上文**不同，语义上就是不同前缀的延续，链式哈希自动
区分，不会张冠李戴。为什么只哈希满块：半满块还会被继续写，
内容会变，哈希会失效——所以设计成"内容封死才注册"，也顺带回
避了 vLLM 论文里共享增长块需要的 copy-on-write（见 Q18）。
碰撞防御：xxhash 64 位理论上可撞，查表命中后再用 token_ids 全
量比对一次，拿 1 次内存比较换绝对正确。

**Q15 pinned prefix 是什么？RAG 为什么需要？**

简要：普通缓存块引用归零就可能被新请求挤掉（回收再利用）；
pin 给文档前缀的块加"钉子"（pin_count），保证热文档的 KV 永远
驻留。RAG 里换问题不换文档，热前缀命中 = TTFT 稳定地低。

详细：先分清两者回答的问题——**前缀缓存命中**回答"这次请求
能不能复用已有 KV"（读路径、自动、概率性）；**pin** 回答"这块
KV 会不会被回收"（淘汰路径、显式、保证性）。命中挡不住回收。
时间线例子（显存 100 块，文档 D 占 75 块）：t1 问 D 的第 2 个
问题 → 哈希命中、数据未被动过 → TTFT 秒级；t2 别的长请求把
空闲池耗尽 → 分配器回收了"没人引用"的 D 的 75 块（KV 被覆盖）；
t3 再问 D → 哈希查到了但 token 复核失败 → MISS → 整篇重算，
TTFT 飙回冷启动水平——这就是**抖动**：同一文档，时快时慢，
取决于别人的流量。加 pin 后：pin_count 让引用计数永远 ≥1，
块永远不进空闲池，t3 变成稳定命中。通用引擎只能用 LRU 猜冷热
（vLLM V1 的 radix cache），但 RAG 的"同文档连续几十问"这个
模式应用层最清楚——所以做成显式 `pin_prefix(doc)` API，把领域
知识焊进引擎。代码上就是两个计数的分工：ref_count 管"有人在
用吗"（归零可回收），pin_count 管"永远视作有人在用"。

**Q16 Prefill/Decode 为什么要差异化数据通路？**

简要：prefill 一次算一整段（变长、compute-bound，走 varlen
FlashAttention，cu_seqlens 描述边界）；decode 一次算每序列 1 个
token（形状固定、memory-bound，走单查询 paged kernel + CUDA
Graph）。两条路的输入打包、缓存访问、kernel 形态完全不同。

详细：prefill 像**通读全文做笔记**——一段 prompt 几百上千 token
一起进来，批内序列长短不齐，用"前缀和数组"（第 i 个序列从哪
到哪）划界，FlashAttention 一次处理，算力吃得满；decode 像
**逐字听写**——每步每序列只来 1 个新 token，计算少但要翻全部
笔记（读 KV），瓶颈在内存带宽，且形状每步都一样 → 正好适合
录成图回放。混着做会两头不讨好：decode 复用 prefill 的大 kernel
浪费 99% 算力，prefill 用 decode 的小 kernel 要跑几百步。这条
差异线也解释了后面所有架构选择（投机验证属于"一次 K+1 个"的
中间形态，所以有了专门的第三条通路 Q3）。

**Q17 投机轮次的 trim/rollback 怎么工作？**

简要：草稿先把序列"撑长"，验证后按接受结果把 token_ids 截回
确认长度；块表用 trim_to 裁到对应块数并清掉半满尾块的哈希；
draft 模型侧（若用）有自己的平行块表同步裁。块内"多写的脏 KV"
无害——下轮会在同一位置覆盖，注意力长度由确认后的 context_len
决定，不会读到。

详细：类比 **Word 的撤销**：草稿是"打了 5 个字还没保存"，
验证接受 3 个 → 保留 3 个，剩下 2 个删掉。显存侧要小心两件事：
①块表可能为草稿多领了块——必须还回空闲池（否则泄漏，几轮就把
缓存池吃空）；②如果草稿恰好把某块"写满"了，按常规逻辑会给它
注册哈希、进前缀索引——**但它的内容还没被确认**！未来请求可能
错误命中这段"幻觉前缀"。所以 trim 时凡落在确认长度之后的哈希
一律清除。反过来，被确认的内容跨过块边界时要**补**注册哈希
（正常路径由 append() 做，投机路径绕过了它，trim_to 补上）——
一删一补，这就是我们说"块表不变式"的含义。

**Q18 统一采样器为什么用 Gumbel-max？**

简要：`argmax(probs / exponential噪声)` 数学上等价于按概率抽样，
但全程是张量运算（没有 multinomial 的宿主同步），能进 CUDA
Graph；贪心分支用 `torch.where` 在图内切换，温度=0 先替换成 1.0
防除零。

详细：要从概率分布"抽签"，朴素做法 `torch.multinomial` 会做
宿主侧同步（返回大小取决于语义、难进图）。Gumbel-max 技巧：
给每个 logit 加上独立同分布的 Gumbel 噪声（实现上
`−ln(−ln(U))`，我们的指数噪声版本是等价变形），取最大——经典
结论 P(第 i 个最大) = p_i，**加噪声取最大 = 按权重抽奖**。直觉：
噪声偶尔让小概率 token 翻上来，翻上的频率恰好等于它的概率。
工程上它是"一次 elementwise + 一次 argmax"，没有数据依赖的
扫描，kernel 极友好。贪心（T=0）是特例：直接 argmax，不能真除
以 0（inf→NaN→argmax 恒 0，这是我们修过的真实 bug），先
`where(greedy, 1.0, T)` 把无效温度换成安全值。

**Q19 [vLLM 高频] vLLM 的 PagedAttention 实现细节？copy-on-write 和 radix cache？**

简要：vLLM 论文机制与我们同构（块表/分配器/引用计数）；差异点：
①它允许共享"还在增长的尾块"，两个序列都要写时触发 copy-on-write
（谁写谁整块复制）；我们只共享封死的满块，追加永远进新块，
设计上消灭 CoW。②前缀索引 v0 用块哈希（与我们同构），V1 换成
radix tree + LRU，支持任意长度部分命中与有原则的淘汰。

详细：CoW 的存在是因为 vLLM 要服务并行采样/beam search——同一
序列 fork 出多个候选分支，共享前缀的同时各自生长尾块；引用
计数 >1 的块被写入前必须复制。这与操作系统 fork 后写时复制
内存页完全同构。我们垂直场景没有"一个请求内多分支"的需求，
干脆规定**可共享的前提是内容不可变**，尾块永远独占——用一点
共享粒度（两个活跃请求若有相同的未封口前缀不合并）换掉整条
CoW 路径。radix cache：把所有见过的前缀按 token 组成一棵基数树，
新请求沿树匹配到最深节点即拿到全部可复用块；叶侧按 LRU 淘汰
腾显存。我们的链式哈希等价于**隐式**radix（父哈希就是树边），
但没有 LRU——用 pin 显式管理冷热（Q14），改进方向就是 LRU 化，
这题答"我知道差距且知道怎么补"即满分。

## 第三章 公平三方基准（简历第 3 条）

**Q20 三方对比怎么保证公平？踩过什么坑？**

简要：五同——同权重精度（bf16/fp16）、同 token 序列（预分词，
绕开各家 tokenizer 差异）、同 GPU（Ollama 起专用实例绑定同一块
卡，避免默认 Q4 量化/CPU 回退）、同解码（贪心 + 投机无损 → 结果
逐 token 可比）、进程隔离 + 3 次取中位；vLLM 配置完全对等的投机
参数（同 K、同 n-gram 上下界）。踩过的坑：Ollama 默认再套一层
chat 模板（双重模板）→ raw 模式；共享 GPU 邻居负载 ±15% 波动 →
终测背靠背重跑；离线吞吐 ≠ 在线 goodput → 明确口径。

详细：基准最大的敌人是**"默认值不等价"**：Ollama 默认 Q4 量化
（跟 bf16 比是欺负它）、默认走 CPU 回退、默认给 prompt 再包一次
对话模板（同一个"问题"变成两套格式）——每一项都能造成数倍
偏差，而论文式的柱状图根本看不出来。我们的方法是"**把每个
默认值显式钉死**"：精度钉成 fp16、模板钉成 raw、GPU 钉成同一
块、prompt 钉成同一条 token 序列。第二个敌人是**环境噪声**：
共享 GPU 上别人的任务让数字抖 ±15%，我们的第一次"领先 17%"就
在干净复测后回归持平——所以最终数字用同条件背靠背重跑。第三
个敌人是**口径**：离线打满批的吞吐天然高于在线按 SLO 的
goodput，报告里写明是离线口径。这套"五同 + 三坑"本身就是面试
加分项：它证明你测过的数字是可辩护的。

**Q21 为什么选 vLLM 和 Ollama 当对手？**

简要：vLLM 是通用批处理吞吐的技术上界（面试官的参照系）；Ollama
是单用户小模型部署的事实标准（我们目标场景的 incumbnent）。
赢 Ollama = 垂直定位成立；与 vLLM 持平单请求 + 交代交叉点 =
诚实地划清适用边界。

详细：选对手的本质是**给数字选坐标系**。只跟弱者比没意义，
只跟 vLLM 比吞吐会被批处理优势淹没。我们场景（知识库问答：
单卡、batch 1–8、按需启停）的真实竞品是 Ollama——它是开发者
本地跑小模型的默认选择，且和 vLLM 代表了两种极端：极致易用
（单用户、无投机、无前缀管理）vs 极致吞吐（大 batch、异步调度）。
把两个都放进图里，我们的位置（单请求持平 vLLM、全批次数倍于
Ollama、冷启动快一个量级）就构成一句清晰的产品陈述，而不是
一个孤立数字。

**Q22 RAG workload 怎么设计的？**

简要：确定性生成一份 ~1200 token 的伪维基文档（30 组事实反复
编织），8 个问题各自问其中一条事实，要求"引用原文回答"——
答案天然是文档片段的复述，正好触发 n-gram 投机的高接受率
（63–90%）；贪心解码让三个后端输出可逐 token 对齐。

详细：workload 要同时满足三个性质：**确定性**（每次跑同一份
文档同一批问题，中位数才有意义）、**负载真实**（前缀长、共享、
答案短且抽取式——这是生产 RAG 的统计形状，不是随机 token 的
toy）、**可比性**（贪心 + 无损投机 → 三家输出应当一致或可解释
地不一致）。其中"答案复述文档"是刻意放大的场景特征——它是我
们 n-gram drafter 的收益前提，面试被问"是不是给自己出题"时坦
然承认：是，这正是"垂直"的含义——先选定负载形状，再让引擎
为它特化；同时报告里如实包含通用负载会掉回 plain 水平的结论。

## 第四章 性能实测与"为什么强"（简历第 4 条）

**Q23 逐个数字解读你的实测结果。**

简要：①投机自加速单请求 2.28×（198→452 tok/s）：接受率 73%
下单轮平均收 ~2.7 个 token；②vs Ollama 全批次 4.8–7.0×：
它无投机/无前缀钉驻/llama.cpp 单流；③vs vLLM 单请求持平
（452/441/463 同噪声带）：投机对投机的公平对决；④冷启动
3.1s vs 44.9s（14.5×）：通用性税的差距；⑤batch≥2 吞吐输
1.4–2×：异步调度与混批的结构差，交叉点如实报告。

详细：每个数字都要能拆到机制：2.28× 不是拍脑袋——每轮成本
≈ 一次图回放（~几 ms）+ 拒绝采样与记账（CPU ~ms 级），产出
= 接受数（2.3–5.7 个/轮随 batch 增长），相比 plain 每 token
一次回放，除一下就是这个数。vs Ollama 的倍数随 batch 变大还
在涨（4.8→7.0×），因为它是单请求架构，并发靠多实例/排队，
批处理红利吃不到。vs vLLM 的持平值得多说一句：我们用 3.5k 行
和它 200k 行在它并非短板的场景（batch=1）打平，说明单请求
瓶颈（派活开销）上"全图化"策略有效；而它 batch≥2 的领先是
overlap scheduler（CPU 调度与 GPU 执行流水）+ chunked prefill
的结构红利，我们单线程调度摊不平固定开销。冷启动的 44.9s 里
大头是它的多桶图捕获与编译栈预热——通用性的固定税。

**Q24 和 vLLM / Ollama / SGLang 比，优势和劣势各是什么？**

简要：先给定位再比维度——我们不是"更好的 vLLM"，是"这个负载切片
上更合适的引擎"。vs vLLM：单请求持平 + 冷启动 14.5× + 代码 3.5k 行
可拥有；批量吞吐输 1.4–2×。vs Ollama：全批次 4.8–7×（它无投机、
无前缀钉驻、单请求架构）。vs SGLang：未直接对比（诚实），其强项
在 radix 前缀与结构化输出前端，与我们的投机全图化是不同维度。

详细：竞品分析的正确姿势是**先说每个对手的结构性优势**（证明你
懂它），再说自己切片为什么绕得开：vLLM 的批处理与异步调度是为
"高并发稳态吞吐"造的，单请求/按需启停场景用不上这些红利但照付
成本；Ollama 的易用性护城河在"开箱即用 + 模型生态"，推理层是
单请求架构，批处理红利为零；SGLang 在前端（FSM 约束解码、
结构化输出）和 radix 复用上领先，底层吞吐与 vLLM 同级。我们的
位置：负载特征明确（RAG 三特征）+ 全链路可控 → 用投机复述、
前缀钉驻、全图化三件套换"单请求持平 + 启动快一个量级 + 资源省"。
劣势也要主动说完整：架构上仅 Qwen3、调度单线程、无量化/长上下文
优化——这些是"还没做"，batch≥2 的差距才是"结构性输"，两者分开
表述显得清醒。

**Q25 [必考] 结构层面，凭什么比 vLLM 强？**

简要：一句话——"vLLM 的强是通用平台的强，其成本结构与我的
垂直负载错配"。四点：通用性税是固定成本（它修复=砍通用性，
无解）；batch=1 瓶颈在派活开销，恰好是全图化的主场；垂直信息
的复利（投机上限=负载可复述比例，是场景属性）；全栈工程速度
（小时级特化 vs 周级走通用抽象）。边界：批量吞吐如实输，
交叉点已测。

详细：见速查版 A6，面试必须练成 30 秒脱稿版。补一个表达技巧：
先说"哪里不如它"再说"哪里强"，可信度翻倍——考官听到你主动
交代 batch≥2 输 1.4–2× 之后，你后面说的每个优势都会被当成
"经过审视的事实"而不是"王婆卖瓜"。

**Q26 [vLLM 高频] 什么是 continuous batching？和 static batching 差在哪？**

简要：static batching：凑一批一起进、全部生成完一起出——短请求
全程陪跑长请求，头尾都在浪费；continuous batching：每个解码步
动态重组批——完成的立刻离开、新到的立刻插队，GPU 每一步都是满批。
它是 vLLM 吞吐优势的基础设施，也是我们调度器学习的原型。

详细：类比**拼车 vs 公交**：static 像包车——满员发车、最后一
位乘客到终点才返程，先下车的干等；continuous 像公交——每站有人
下就有人补位，车永远接近满载。代价是调度复杂度：每步要重算批的
全部元数据（谁还在、块表怎么对齐 padding、序列边界数组），所以
vLLM 的调度器那么厚、还要配 overlap scheduler 把这些 CPU 活藏到
GPU 执行的影子里（Q27）。我们的调度是它的简化版（prefill 优先 +
两级队列 + 抢占），batch≥2 的差距一部分就源于此——能把自己的
简化与对方的完整版放在同一张图里讲清楚，比背定义有说服力得多。

**Q27 [vLLM 高频] vLLM 为什么快？一句话性能观。**

简要：它把推理当作**显存布局与调度问题**而非算子优化问题——
PagedAttention 管"放得下且共享"，continuous batching + chunked
prefill 管"GPU 一直有活干"，CUDA Graph 管"派活的开销"。我们
全盘接受这个框架，再在垂直负载上加投机与全图化验证。

详细：展开三件套：①放得下（Q12 分页）；②有活干——continuous
batching：每步动态重组批（完成就走、新来就进，不等整批齐），
chunked prefill 把长 prefill 切片混进 decode 的 token 预算防
饿死；③派活便宜（piecewise CUDA Graph）。理解"性能观"的层次
比背清单重要：2014 年前的直觉是"优化算子"，vLLM 的洞察是
"LLM 推理的利用率瓶颈在系统层（碎片/空转/launch），不在算子层"
——这也是为什么我们复刻它的系统框架 + 加垂直特化就能在单请求
上追平，而不用去拼更快的 kernel。

**Q28 [vLLM 高频] V1 的 overlap scheduler 为什么关键？**

简要：CPU 调度（选批、建块表、拷数据）与 GPU 上一步的执行
错步流水：GPU 跑第 i 步时 CPU 已在准备第 i+1 步，消掉每步的
同步间隙。这是我们 batch≥2 输掉的主因，也是我们路线图的第一
刀。

详细：我们引擎每步是串行的：CPU 准备（毫秒级 Python）→ GPU 执行
（毫秒级）→ CPU 再准备……GPU 在 CPU 干活时是闲置的。单请求时
两边都不满无所谓；batch 大了 GPU 单步变长，但 CPU 开销不变
（本来就不随 batch 涨多少）→ 理应摊平——问题是我们的 CPU 段
里有"等 GPU 结果才能继续"的硬依赖（采样结果回 CPU 决定下一
步调度）。vLLM V1 用**一步错位**打破依赖：调度用的是"上一步
开始时已知"的信息，采样结果异步处理（async output processing），
CPU 永远在为"下一步"工作而不是等"这一步"。追上它的路径不是
优化 Python 速度，而是重排依赖——这也是 H1 开放题的标准开头。

**Q29 [vLLM 高频] chunked prefill 解决什么？**

简要：长 prefill 是一整块几百 ms 的计算，期间同批 decode 全部
停摆（TPOT 尖刺）；把它切成 token 预算内的片，与 decode 混批
穿插执行，长请求不饿死短请求，SLO 平稳。是我们输掉 batch≥2
的第二结构性原因。

详细：想象一条单车道隧道：prefill 是一辆超长货车，decode 是
一串小轿车——不切的话小轿车要等货车完全通过（几十上百 ms，
对交互用户是可感知的卡顿）。vLLM V1 把"隧道通行权"改成了
**每单位时间发放固定名额**（max_num_batched_tokens 预算），货车
拆成若干车节逐轮通过，小轿车见缝插针。代价是 prefill 总时间
略变长（吞吐换延迟平稳），通用引擎愿意付这个代价保 SLO；我们
垂直场景 prefill 几乎全被前缀缓存消掉（文档 pin 住），所以暂时
不需要——又一个"负载信息决定设计"的例子。

## 第五章 补充高频机制（跨条目）

**Q30 CUDA Graph 捕获有什么约束？你踩过最难的坑？**

简要：约束——被录代码的控制流必须完全固定（无 Python 分支）、
输入必须是预分配静态张量的原地更新、捕获期创建的张量必须保活。
最难的坑：按桶捕获时循环内创建的 cu_seqlens 张量被 Python 回收，
图里记录的是裸地址 → 回放静默读已释放显存 → logits 全 NaN 且
无任何报错。定位靠"hidden-tap"：给图内加中间量导出探针，二分
出问题在图参数生命周期。修复：显式保活列表。

详细：CUDA Graph 是"录像重放"，录像带记的是**地址**不是对象——
Python 变量没了，显存可能被分配器转手给别人，录像还在往老地址
读写。这类 bug 的恐怖在于**无报错、不稳定、随分配节奏漂移**。
排查方法论（可迁移到任何"静默错误"）：①先造对照——同一输入
eager 跑一遍 vs 图跑一遍，确认差异来自图；②打点二分——在图内
插入"把中间结果拷到外部静态缓冲"的探针，第一层就 NaN 说明问题
在输入/参数而非计算；③收窄假设——只剩"图读到的输入和我以为
的不同"，检查每个捕获期对象的生命周期。另外两个图坑也值得备
着：桶选择误选过大图（未填充行带着捕获期残留值参与计算）、
padding 行 slot 残留 0 把垃圾写进物理块 0 污染真实序列（表现：
永远输出同一个 token）。

**Q31 bf16 数值精度：你的对齐测试说明了什么？**

简要：与 HF 贪心比，argmax 一致、logit 差 0.3–0.7——来自
Triton 与 SDPA 求和顺序不同的舍入；平坦 top-2（gap<0.1）上续写
会分叉，属自研 kernel 正常水位。真正的硬指标是同引擎内
投机 vs 普通逐 token 一致（无损性），我们以此为准。

详细：浮点加法不结合——同一串数换个求和顺序结果略有不同，
bf16 只有 8 位尾数，误差更肉眼可见。三家实现（HF/我们/vLLM）
的 attention 归约顺序都不同，所以"完全逐 token 一致"在原理上
就做不到；但**模型是否正确**看的不是绝对值而是"分布有没有
被系统性扭曲"——argmax 集合一致、top-5 相同、误差零均值，
就说明只是噪声。工程教训（真实 bug）：decode kernel 手工点积
用 bf16 累加，128 项求和误差到 ~1.0，比 top-2 间隔大一个量级，
argmax 随机翻转——修复是两操作数先转 fp32 再乘加；而 `tl.dot`
路径天然 fp32 累加无此问题。这也解释了为什么"贪心投机 = 与
自家 plain 逐 token 一致"是比"对齐 HF"更强也更对的验收标准。

**Q32 长上下文 / 集群扩展会先遇到什么墙？（引路题）**

简要：长上下文——块表膨胀、RoPE 表预算、decode 单 program 串行
扫全 KV（需 FlashDecoding 式 split-KV）；集群——PD 分离、前缀
感知路由、KV 跨机传输。这些在速查版 J/H/K 章有完整答题框架，
此处只需展示"知道墙在哪"。

详细：这题考的是**瓶颈预判**而不是现成答案。思路是把量随
序列长/实例数怎么涨列一遍：KV 显存线性涨（→ 分页已解，量化/
稀疏化接力）、单步注意力代价线性涨（→ 按序列切分并行）、调度
状态空间涨（→ 集中路由 or 分片）、多实例间缓存不共享（→ 前缀
路由 + KV 池）。面试时先问清"多长/多少实例"，再挑对应墙展开
一句，远好于背十页架构。
